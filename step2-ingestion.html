Cloud Data Ingestion, Scope Lock & Canonical Entity Resolution

How Sentinel streams 45,806 cleaned parliamentary records directly from Supabase Cloud Storage, enforces the Data Scope Lock, and builds linked Canonical Work Profiles across 12 independent CSV datasets.

Supabase Cloud Storage & Zero-Disk Architecture

To ensure enterprise scalability and eliminate local storage bottlenecks, Sentinel hosts all 12 official parliamentary datasets in a public Supabase Cloud Storage bucket (datasets). The Node.js and Python microservices stream files on demand via high-speed global CDN with an in-memory LRU cache.

Cloud Streaming Pipeline

1. Fast fetch from supabase.co/storage/v1/object/public/datasets/...
2. Stream parsing with PapaParse / Pandas (Chunk size: 1,000 rows)
3. Memory caching with 1-hour TTL (<4ms subsequent query latency)
4. Automatic fallback to local recovery bundles if offline

Data Scope Lock (MVP vs. Phase 2)

MVP Core (Active): 100% tabular fields across 12 CSVs (amounts, dates, categories, vendors, descriptions).
Phase 2 Roadmap: Scanned PDF OCR parsing, raw image binary perceptual hashing (pHash), and external registry connectors (GSTN, MCA21, PFMS).

3-Tier Canonical Entity Resolution Algorithm

Because e-SAKSHI exports split records across separate files, Sentinel runs a multi-tiered resolution algorithm to fuse isolated rows into a unified Canonical Work Profile.

TIER 1 (Exact Work ID Match): Direct relational join on normalized alphanumeric Work ID.
TIER 2 (Composite Key Match): If ID is missing ──► Match (Constituency + Sector + Date ±14d + Cost ±5%).
TIER 3 (Semantic Embeddings): SBERT all-MiniLM-L6-v2 Cosine Similarity > 0.88 across project descriptions.
